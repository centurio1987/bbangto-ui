두 가지 수행안

같은 일곱 조각을 어떻게 굴릴지에 두 길이 있습니다. 둘 다 배치 세 개로 나뉩니다. 배치란 한 번에 묶어 수행하는 work 뭉치이고, 크기는 한 세션 예산의 절반을 넘지 않게 잡습니다.

단일 에이전트 안을 먼저 봅시다. 한 세션이 처음부터 끝까지 순서대로 갑니다. 배치 1이 S1·S2·S3, 배치 2가 S4·S5, 배치 3이 S6·S7 이에요. 병렬 폭은 1이죠. 강점은 목소리가 하나라는 것입니다. 사례 여덟 개를 같은 사람이 쓰니 절차를 적는 형식도 용어도 갈리지 않아요. 약점은 배치 2가 무겁다는 점입니다. 사례 여덟 개의 집필이 배치 하나에 통째로 몰리기 때문에, 예산이 모자라면 S5 를 배치 3으로 미루는 판단을 착수 시점에 해야 하죠. 되돌리기는 쉽습니다. 배치 2까지는 README를 안 건드리고 임시 산출물만 쌓거든요.

오케스트레이션 안은 다릅니다. 여러 워커를 동시에 굴려요. 배치 1에서는 S1 과 S3 이 서로를 안 읽으므로 나란히 돌 수 있어 병렬 폭이 2가 되고, S2 가 S1 을 기다립니다. 배치 2에서는 폭이 4로 올라가죠. 사례 여덟 개를 워커 넷에 둘씩 나누는 것입니다. 배치 3은 대상이 README.md 한 파일이라 나눌 수 없어 순차예요. 강점은 가장 무거운 배치 2가 짧아진다는 것입니다. 약점은 워커마다 절차 서술 형식과 용어가 갈린다는 점이고, 그 차이는 S6 조립에서 통합 재작성으로 청구되죠. 되돌리기는 앞의 안과 같되 단위가 더 잘게 쪼개집니다. 워커 하나의 산출물만 버리고 그 워커만 다시 돌릴 수 있어요.

두 안의 차이를 한 문장으로 좁히면 이렇습니다. 단일 에이전트 안은 배치 2의 무게를 감수하고 목소리를 지키며, 오케스트레이션 안은 목소리의 균열을 감수하고 배치 2를 쪼갭니다.

유저는 오케스트레이션 안을 골랐어요. 그 선택을 받아, 워커 넷이 같은 형식으로 쓰도록 배치 2 문서에 「워커 공통 계약」 네 조항을 박아 뒀습니다. 워커는 레포를 다시 조사하지 않고 S1·S2 산출물만 입력으로 받으며, 출력 형식이 고정되고, 세지 않은 숫자를 쓰지 않고, 파일을 직접 쓰지 않습니다.

막힐 만한 지점

가장 큰 것부터 봅시다.

목소리가 갈리는 자리는 배치 2입니다. 워커 넷이 각자 사례를 쓰면 절차를 번호로 적는 방식, 코드 앞에 붙이는 한 줄, 용어 선택이 조금씩 어긋납니다. 공통 계약으로 억제하지만 완전히 막지는 못해요. 남는 차이는 S6 에서 통합 재작성으로 흡수하고, 그 재작성 분량을 수행 내역에 적습니다. 다음에 같은 선택을 할 때 근거가 되어야 하니까요.

예산이 넘칠 자리도 배치 2입니다. 워커 넷이 동시에 돌면서 각자 긴 산출물을 내면 합이 세션 예산 절반을 넘길 수 있습니다. 그래서 워커의 출력은 임시 파일로 떨어뜨리고, 오케스트레이터에게는 경로와 요약만 올라오게 합니다. 전문을 대화에 올리지 않는 것이 이 배치의 예산 방어선입니다.

죽은 코드 조각이 새 문서로 옮겨 갈 위험이 있습니다. 지금 README에도 foundationCatalog['coral'] 처럼 살아 있는지 확인되지 않은 표기가 있어요. 검증 안 된 코드 조각은 문서가 아니라 사람을 헤매게 하는 물건입니다. 그래서 각 사례의 완료 기준에 "코드 블록의 모든 import 토큰이 S1 이 만든 export 목록에 있을 것"을 박았습니다. 하나라도 없으면 그 조각은 미완입니다.

되돌리기 어려운 지점은 사실상 S6 하나뿐입니다. 그 앞의 work들은 임시 파일만 남기고, S6 만 README.md 를 교체합니다. 단일 파일 교체라 되돌림 등급은 깨끗하게 나올 것으로 봅니다. 다만 이건 계획 시점의 예상이고, 실제 등급은 rollback-plan 이 태그를 보고 판정합니다.

마지막으로 검증이 이 카드와 무관하게 빨간 경우가 있습니다. 프로젝트 품질 게이트 다섯 종은 소스를 검사하는데 이 카드는 소스를 안 건드립니다. 그러니 거기서 실패가 나오면 이 카드가 만든 것이 아니라 앞선 상태의 문제예요. 그때 고치려 들지 않고 출력을 그대로 보고합니다.

무엇이 되면 끝인가

검증 다섯 가지가 전부 초록일 때 끝납니다. 하나씩 봅시다.

숫자가 맞는가. 매니페스트 네 개에서 항목 수를 세어 그 값이 README 본문에 그대로 나오는지 대조합니다. 눈으로 보는 대조가 아니라 스크립트가 세고 grep이 찾습니다.

코드가 실제로 컴파일되는가. README의 코드 블록을 임시 파일로 뽑아 워크스페이스 타입 검사에 태웁니다. pnpm build 와 pnpm typecheck 이 둘 다 exit 0이어야 하고, 뽑아낸 임시 파일은 검사 뒤에 남기지 않습니다.

링크가 살아 있는가. README가 가리키는 레포 안의 경로와 문서 앵커가 전부 실재해야 합니다. 깨진 링크는 0건입니다.

집필 규칙을 지켰는가. authoring-kit의 validate 가 갈래 위반 0건을 내고, 기계 리듬 스캐너가 선정된 voice의 면제를 반영한 뒤 임계 아래로 떨어져야 합니다.

기존 게이트가 여전히 초록인가. 이 프로젝트의 CLAUDE.md 가 요구하는 다섯 명령을 돌립니다. 이 카드는 소스를 안 건드리므로 회귀가 없다는 확인 절차예요.

여기까지가 스크립트로 판정되는 것들입니다. 사람만 정할 수 있는 것은 따로 있어요. 어디까지를 README에 담고 어디부터 DESIGN_SYSTEM_GUIDE.md 로 넘길지, 그리고 어떤 voice로 쓸지입니다. 둘 다 검토 단계에서 판단 항목으로 올려 유저에게 묻습니다. 지금 정해 두고 나중에 통보하지 않습니다.

무엇이 문제인가 — 실측

현 README(174줄)는 패키지 목록 + 설치 스니펫이다. 지시가 지적한 셋이 실제로 없다.

  • 패키지 8종이 표 한 줄씩으로만 소개되고, 어떤 상황에 무엇을 고르는지가 없다.
  • style guide를 구현할 수 있다는 사례가 없다. StyleGuideProvider 사용 예 4줄이 전부다.
  • style guide를 저작하는 방법(preset 작성 → 대비 게이트 → 매니페스트 등재)이 한 줄도 없다.

거기에 수치 drift가 겹친다(실측 대조 결과):

| README 기재 | 실측 | 출처 | |---|---|---| | style guide preset 24종 | 51종 | packages/style-guide-catalog/catalog.manifest.json | | 브랜드 프리셋 74종 | 76종 | packages/foundations/foundation.manifest.json | | viz 카탈로그 "Blueprint_Technical_01 등" | 30종 | packages/visualization-style-guide-catalog/catalog.manifest.json | | viz 유형 축 언급 없음 | 87종 | packages/visualization/type.manifest.json |

지시의 목표가 "README만 보고 자기 사례에 맞는 패키지를 골라 style guide까지 구현"이므로, 틀린 수치는 그 자체로 목표 미달이다. 그래서 이 카드는 문장 작업이 아니라 매니페스트를 SSOT(single source of truth, 유일 정본)로 삼는 대조 작업을 포함한다.

  6. 다이어그램·인포그래픽을 그린다 — visualization(87 유형) + viz 카탈로그(30)

제약

  • README 한 장으로 자립한다. 지시의 목표가 "README만 보고"다. 개념 심화는 DESIGN_SYSTEM_GUIDE.md(atom/molecule/block/pattern 기준표)가 이미 있으므로 링크로 넘기고 복제하지 않는다. 어디까지를 README에 담고 어디부터 링크로 넘길지는 검토의 판단 항목으로 낸다.
  • 코드 스니펫은 실제 export를 쓴다. 지금 README의 foundationCatalog['coral'] 같은 표기가 살아있는 API인지 S1에서 대조하고, 죽었으면 고친다. 검증되지 않은 스니펫은 문서가 아니라 함정이다.
  • authoring-kit은 지시된 도구다. 이 프로젝트에 미설치(installed_plugins.json에 bbangto-ui 없음)이나, 사용자 레지스트리 ~/.claude/authoring은 살아 있고 voice 5종이 등록돼 있다. 플러그인 설치는 ~/.claude 공유 상태 변경이라 설치 없이 마켓플레이스 경로의 스크립트를 CLAUDE_PLUGIN_ROOT로 직접 호출한다. spec은 이 프로젝트에 새로 등록한다(.claude/authoring/specs/).

버린 대안

  • docs/ 로 쪼개기 — 사례별 md를 따로 두고 README는 목차만. 지시의 "README만 보고"와 정면으로 어긋나고, KAN-044(문서 정리)가 세려는 문서 수를 늘린다.
  • 자동 생성 — 매니페스트에서 README 표를 생성(KAN-025의 trendTable 선례). 수치 drift는 막지만 사례별 산문 절차는 생성 대상이 아니다. 이번 범위 밖이고, 필요하면 후속 카드로 낸다.
  • 영문 README — 지시에 없다. 기존 문체(한국어)를 유지한다.
