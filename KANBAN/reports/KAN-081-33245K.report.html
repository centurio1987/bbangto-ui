계약 CSS export — 브라우저 없이 정적 렌더할 수 있는 길

voice 미적용 — authoring-kit 이 없어 집필 단계를 건너뛰고 데이터만으로 렌더했습니다. 문체가 다른 리포트와 다를 수 있습니다.

전략

무엇을 내보내는가. 런타임에만 <head> 에 들어가는 스타일시트를 { id, css } 목록으로 내보낸다. id 는 런타임이 쓰는 <style id> 와 같은 값이다. 소비자(정적 렌더)는 이 목록을 <head> 에 그대로 깔고 renderToStaticMarkup 결과를 붙인다.

| 패키지 | 지금 런타임 주입 | 내보낼 것 | | --- | --- | --- | | core | useMotionKeyframes → bbangto-motion-keyframes(MOTION_CSS) | coreStaticStyles() — MOTION_CSS 는 이미 export 지만 id 가 없다 | | visualization | useVizDefs → bbangto-viz-reduced-motion · useVizContractCss → bbangto-viz-contract | vizStaticStyles() | | style-guide-catalog | makeMotifWrappers 의 useMotifStyle → bbangto-<preset>-motif(53개 preset) | motifStylesOf(styleGuide) — 지금 motifCssOf 는 배럴 밖이고 id 를 안 담는다 | | visualization-style-guide-catalog | useVizMotifStyle → bbangto-viz-motif-<preset>(18개 preset) | vizMotifStylesOf(vizStyleGuide) |

한 값에서 두 길이 나온다. 훅이 주입하는 글자와 export 가 주는 글자가 같은 상수에서 나와야 한다. 사본을 두면 언젠가 한쪽만 고쳐진다. 그래서 훅이 export 목록을 읽어 주입하게 바꾼다(구조로 같게 만든다). 거기에 더해 브라우저에서 실제로 들어간 <style> 과 export 를 견주는 테스트를 둔다(구조가 깨져도 잡히게).

제약.

  • 기존 API 는 그대로 둔다(추가만). 훅 이름 · style id · 주입 시점(useInsertionEffect / useEffect)을 안 바꾼다 — 런타임 결과가 바이트까지 같아야 소비자의 1단계 경로가 안 흔들린다.
  • 목록의 순서는 한 패키지 안에서 런타임 주입 순서와 같게 둔다. 패키지 사이 순서는 소비자가 정한다(런타임에서도 렌더 순서에 달려 있다).
  • 프리셋 파일 71개를 손으로 고치지 않는 쪽을 먼저 찾는다. style-guide-catalog 는 makeMotifWrappers 한 곳에서 등록하면 된다. viz 카탈로그는 프리셋마다 useVizMotifStyle(MOTIF_ID, MOTIF_CSS) 를 부르므로 등록 자리를 S4 에서 정한다(가이드 객체를 키로 하는 WeakMap 이 1안).

버린 대안.

  • 소비자가 dist 에서 정규식으로 긁기 — 패키지 내부 구조에 묶이고 모티프 id 는 프리셋마다 자리가 달라 깨지기 쉽다(소비 측에서 먼저 버렸다).
  • 서버 렌더 중에 <style> 을 인라인으로 내는 컴포넌트 — 런타임 경로가 바뀌어 1단계 결과가 달라지고, 같은 시트가 여러 번 들어간다.
  • 가이드 객체에 motifCss 필드 추가 — 공개 타입(StyleGuide · VisualizationStyleGuide)이 바뀌어 다른 소비자에게 번진다. 함수로 꺼내는 쪽이 범위가 좁다.

릴리스. 네 패키지 minor 변경셋. 배포(publish)는 유저에게 따로 묻는다.

경로 겹침은 신호이지 판정이 아닙니다. DB 스키마·환경변수·패키지 매니페스트·공유 API 계약처럼 경로에 드러나지 않는 의존은 여기 잡히지 않습니다.
