# KAN-071-FK1W8K — 앱 에이전트의 라이브러리 이탈·개선 요청 실제 사례 재현 — 저장소 열람과 구현까지 연 시험

## 전략
### 문제

KAN-067 S5 는 앱 폴더만 읽고 방침만 내게 한 시험이라, 고치기 전 배포물로도 현상이 나오지 않았다. 이 카드는 현상이 실제로 나온 세션을 같은 조건으로 다시 돌린다. 2026-10-10 다른 프로젝트의 대화 기록에서 두 사례를 찾았고, 유저가 둘 다 재현하기로 정했다.

두 사례의 저장소는 비공개다. 이 문서에는 라이브러리 쪽 사실만 적고, 지시문 원문·앱 파일·시험 기록 원본은 저장소 밖 비공개 폴더에 둔다(「제약」).

- **사례 A — 앱 구현 중 결정** (모델 `claude-opus-5-5`, 2026-09-30~10-04)
  - 앱 카드의 전략을 세우는 단계에서, bbangto-ui 저장소는 고치지 않고 모자란 것은 그쪽에 요청한다는 방침을 먼저 정했다. 컴포넌트 분해 작업에도 「bbangto-ui 에 요청할 것」 칸을 미리 뒀다.
  - 분해 결과는 화면 조각 42개 중 「있음 11 · 앱에서 만듦 22 · 요청 9」였다. 그리고 bbangto-ui 를 런타임에 들여오지 않고 같은 이름의 컴포넌트를 앱에서 새로 짓는 안을 골랐다.
  - 근거로 읽은 것은 로컬 `~/bbangto-ui` 소스와 설치된 core 1.1.2 의 dist 였다. README 와 매니페스트는 읽지 않았다.
  - 그때 든 결함 둘(`Button` 하나에 419,703 B · Provider 의 외부 글꼴)은 KAN-051~055 가 고쳐 core 1.2.0 으로 배포했다. 요청 9개는 접근성·변형이 모자란 기존 컴포넌트였다(서랍 포커스, 탭·선택 상자 키보드, 입력칸 라벨 연결 등).
- **사례 B — 앱 기획 중 결정** (모델 `claude-fable-5-1`, 2026-10-08)
  - `~/bbangto-ui/README.md` 앞 80줄을 읽었다. 그 안에 길잡이 표의 「이 레포에 기여한다」 줄(그때 28번째 줄)이 있다.
  - 기획 문서에는 그래프 자동 배치 기능이 없으면 다른 배치 라이브러리를 더한다고 적었고, 이어진 보고서에는 bbangto-ui 에 없는 부품은 bbangto-ui 저장소에 기여해 넣는다는 방침을 적었다.
- **둘의 공통점**
  - 둘 다 npm 배포물이나 GitHub 이 아니라 로컬 저장소 `~/bbangto-ui` 를 읽었다. 그래서 배포 README 수정(KAN-067)은 두 사례의 읽기 경로에 없었다.
  - 두 앱 저장소에는 `CLAUDE.md`·`AGENTS.md` 가 없다. 지시는 전역 `~/.claude/CLAUDE.md` 뿐이었다. 이 파일은 2026-09-26 이후 바뀌지 않았으므로 지금 파일이 그때 파일과 같다.
  - 사례 A 의 「고치지 않고 요청한다」 방침은 전역 지시 규칙 2(「다른 프로젝트에도 영향을 주는 파일을 고칠 때는 분명한 실행 요청이 있어야 한다」)와 문구가 거의 같다. 그 규칙이 결정을 끌었는지는 확인 안 함이다.

### 접근

1. **시험 세션은 앱 사본 폴더에서 `claude -p` 로 따로 띄운다.** 모델은 사례와 같게 두고, 지시문은 실제 세션의 원문을 그대로 쓴다. 하위 에이전트로 돌리지 않는 이유는 실제 세션처럼 전역 지시·스킬·갈고리를 그대로 받게 하기 위해서다. 인증과 `HOME` 은 건드리지 않는다.
2. **`~/bbangto-ui` 는 갈고리로 조건별 사본에 잇는다.** `--settings` 로 붙인 PreToolUse 갈고리가 도구 입력의 `~/bbangto-ui`·`$HOME/bbangto-ui`·절대 경로를 사본 경로로 바꾼다. 2026-10-10 탐침에서 Bash `cat ~/bbangto-ui/…` 와 Read `/Users/centurio/bbangto-ui/…` 가 둘 다 사본을 읽었고, 진짜 저장소에는 아무것도 생기지 않았다. 같은 갈고리가 도구 호출을 전부 남기므로 무엇을 읽었는지 그 기록으로 센다.
3. **공개 저장소에 실제로 요청이 나가지 않게 막는다.** `gh` 와 `git push` 를 금지한다. 막힌 시도는 기록해 「개선 요청」 결론의 신호로 센다.
4. **조건은 셋이다.** T0 과 T1 을 견주면 라이브러리 결함 수정의 효과가, T1 과 T2 를 견주면 README 수정의 효과가 나온다.

   | 조건 | 사례 A — `~/bbangto-ui` 사본 · 설치 버전 | 사례 B — `~/bbangto-ui` 사본 |
   |---|---|---|
   | T0 그때 | `9bce7a8`(2026-10-04 18:20 시점 main) · core 1.1.2 · tokens 1.3.0 | `06649dc`(2026-10-08 02:00 시점 main) |
   | T1 README 고치기 직전 | `fc7a352`(KAN-067 병합 직전) · core 1.2.1 · tokens 1.4.0 | `0a81094`(배포 README 는 고쳤고 루트 README 는 고치기 전, KAN-072 의 기준점) |
   | T2 지금 | main · core 1.2.2 · tokens 1.5.0 | main |

5. **재현 지점은 결정이 난 자리다.** 사례 A 는 두 곳이다. 하나는 유저의 첫 지시로 카드 전략을 세우는 자리이고, 「요청할 것」 칸이 생기는지 본다. 다른 하나는 컴포넌트 분해 작업자 지시문이고, 분해 수·런타임 사용 여부·요청 수를 본다. 사례 B 는 기획서 지시를 낸 뒤 같은 세션에 보고서 지시를 이어서 낸다(`--resume`). 지시문에 구현이나 열람을 막는 말은 넣지 않는다.
6. **T0 을 먼저 사례마다 한 번 돌린다(파일럿).** 원 세션은 무겁다. 사례 A 의 분해 작업자는 모델 호출 113번에 15분이 걸렸고, 사례 B 는 보고서 지시까지 호출 64번이었다. 그래서 파일럿에서 토큰과 시간을 잰 뒤 반복 횟수를 정한다. T0 에서 현상이 나오지 않으면 T1·T2 로 가지 않는다. 그때는 하네스와 실제 세션의 차이를 적고 멈춘다.
7. **결론은 넷으로 나눈다.**
   - 앱 안 확장: bbangto-ui 를 들여와 감싸거나, 토큰·atom 으로 만든다.
   - 앱에서 새로 짓기: bbangto-ui 를 들여오지 않고 대체품을 만든다.
   - 다른 라이브러리를 더한다.
   - 개선을 요청하거나 저장소에 기여한다.

   산출물 글과 도구 기록에서 센다. 「원하는 것이 없을 때」 절과 루트 README 길잡이 줄을 읽었는지도 함께 센다.

### 제약

- **비공개 두 저장소의 내용은 이 저장소에 커밋하지 않는다.** 지시문 원문·앱 파일·시험 기록 원본이 여기에 든다. bbangto-ui 는 공개 저장소다. 원본은 저장소 밖 비공개 폴더에 두고, 이 문서에는 라이브러리 쪽 사실과 수치만 적는다.
- 진짜 `~/bbangto-ui` 와 두 앱 저장소는 읽기만 한다. 사본은 비공개 폴더에 만든다. main 체크아웃은 여러 세션이 함께 쓰는 자리라 옛 커밋으로 돌리지 않는다.
- 전역 `~/.claude/CLAUDE.md` 는 고치지 않는다. 규칙 2 의 영향은 사례 A 산출물이 그 규칙을 근거로 드는지로만 본다.
- 결과가 매번 같지 않으므로 게이트가 아니라 기록이다.
- 라이브러리 코드와 문서는 고치지 않는다. 남은 원인이 나오면 후속 카드 후보로 적는다.

### 버린 대안

- **하위 에이전트(Agent 도구)로 돌린다.** 실제 세션과 같은 전역 지시·스킬·갈고리 환경을 받는다고 보장할 수 없다.
- **`HOME` 을 사본 폴더로 바꿔 `~/bbangto-ui` 를 통째로 갈아 끼운다.** 로그인이 풀린다(2026-10-10 탐침 「Not logged in」). 키체인을 잇는 방법은 자격 증명을 다루는 일이라 쓰지 않는다.
- **진짜 `~/bbangto-ui` 를 옛 커밋으로 돌린다.** 다른 세션이 쓰는 main 체크아웃을 바꾸게 된다.
- **GitHub 을 실제로 열람하게 한다.** 두 사례 모두 GitHub 을 읽지 않았다. 그리고 GitHub 의 main 은 한 시점만 보여 줘서 조건을 가를 수 없다.
- **원 세션 결과를 「고치기 전」으로 쓰고 지금만 다시 돌린다.** 하네스 차이와 수정 효과를 가를 수 없다.
