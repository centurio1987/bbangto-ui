# KAN-066-T6NR80 — 워크스페이스 소스 경로 해석 — 새 워크트리에서 build 없이 typecheck·test:unit 통과

## 전략
**패키지끼리 서로를 찾을 때 개발 도구만 소스를 보게 한다. 배포물과 Storybook 은 지금처럼 dist 를 본다.**

1. **개발용 조건 이름 `bbangto-source`.** 각 `package.json` exports 의 진입점마다 `"bbangto-source": "./src/…ts"` 를 맨 앞에 둔다. 조건은 앞에 적힌 것부터 맞춰 보기 때문이다. 이 이름을 켜는 곳은 셋뿐이다: 루트 tsconfig 의 `customConditions`(typecheck), 각 패키지 vitest 의 `resolve.conditions`(test:unit), 매니페스트 생성기를 돌리는 tsx 의 `--conditions`. Storybook·tsup 안의 esbuild·쓰는 쪽 번들러는 이 이름을 모르므로 dist 를 그대로 읽는다.
2. **번들 크기 게이트는 build 끝으로 옮긴다**(2026-10-10 유저 선택). 루트 `pnpm build` 가 7개 패키지를 다 빌드한 직후 크기를 잰다. 그러면 test:unit 은 소스만 보게 되어 dist 없이 돈다. 게이트 5종의 이름과 순서는 그대로다.
3. **조건 누락은 게이트로 막는다.** 새 서브패스를 더하면서 조건을 빠뜨리면 그 서브패스만 다시 dist 를 찾고, 그 사실은 새 워크트리에서야 드러난다. 저장소 전역 게이트 자리(foundations 의 `metadataCoverage`·`bundleBudget` 과 같은 자리)에 「TS·JS 진입점마다 조건이 있고, 그 조건이 가리키는 소스 파일이 있다」를 보는 단위 테스트를 둔다.
4. **KAN-064 가 넘긴 생성기의 dist 의존도 같은 조건으로 푼다.** 생성기가 `../src/index` 를 거쳐 다른 패키지를 dist 로 읽는다(KAN-064 전략 3). tsx 에 같은 조건을 켜면 build 순서와 상관없이 돈다.

### 착수 전 실측 (2026-10-10, dist 를 지운 워크트리)

- typecheck: tokens·hooks 만 통과한다. 오류는 foundations 87 · core 113 · visualization 13 · style-guide-catalog 71 · visualization-style-guide-catalog 90건이고, 전부 TS2307(모듈 없음)과 그 여파다.
- test:unit: 다른 패키지를 못 찾아 실패하는 파일(visualization 2 · style-guide-catalog 5 전부 · foundations 일부)과 번들 크기 게이트 7건.
- 시험: tokens·core·visualization 에 조건을 붙이고 루트 tsconfig 에 `customConditions` 를 켜자 foundations·core·visualization 의 typecheck 오류가 0건이 됐다. visualization vitest 에 조건을 켜자 25파일 285건이 통과했다. 같은 설정으로 빌드한 foundations `.d.ts` 는 tokens 를 외부 import 로 둔다.
- 같은 소스를 두 번 빌드해도 core·visualization dist 파일 200개의 해시가 다르다(청크 분할 출력이 매번 다르다). 그래서 배포물 확인은 해시가 아니라 import 문·`.d.ts`·`npm pack` 목록으로 한다.

### 제약

- 배포되는 `package.json` 에도 조건 줄이 실린다. 가리키는 src 는 배포 파일에 없지만, 쓰는 쪽이 같은 이름을 켜지 않으면 읽히지 않는다. 쓰는 쪽에 바뀌는 동작이 없으므로 changeset 은 내지 않는다. 문제가 되는 도구가 나오면 배포 직전에 그 줄을 빼는 단계를 더한다.
- vitest 의 `resolve.conditions` 는 기본 조건을 덮어쓴다(Vite 6 이후). 기본 조건을 함께 넣어야 react 같은 의존이 지금처럼 풀린다. 확인 안 함 — S2 에서 hooks(jsdom)로 본다.
- Storybook 설정은 건드리지 않는다. 배포물 그대로 시험한다는 지금 설계를 유지한다.
- scope 는 이 워크트리에서 정했다. 병합하기 전까지 main 의 `dep-check` 에는 보이지 않는다.

### 버린 대안

- **루트 tsconfig `paths`**: 배포 `package.json` 을 안 건드리는 장점이 있다. 그러나 시험하니 rootDir 밖 파일 오류(TS6059)가 core 9 · style-guide-catalog 251 · visualization-style-guide-catalog 537건 났고, vitest 별칭도 따로 맞춰야 한다.
- **크기 게이트를 6번째 게이트로 분리 · dist 가 없으면 건너뜀 · 목표를 typecheck 로 좁힘**: 유저가 build 끝에 붙이는 안을 골랐다. 건너뛰기는 KAN-051 이 일부러 정한 「건너뛰지 않고 실패」를 되돌린다.

지시 원문은 `KANBAN.md` 카드의 `원문:` 블록에 있다(중복 보관하지 않음).

## 검증
명령은 `bash -c '…'` 로 돌린다(zsh 는 변수를 낱말로 안 쪼갠다). dist 를 지울 때는 `ls -d packages/*/dist` 로 경로를 확인한 뒤 절대경로로 `rm -rf` 를 따로 친다.

### build 없이 (카드 목표)

1. dist 를 모두 지운 뒤 `pnpm typecheck` rc=0.
2. 이어서 build 없이 `pnpm test:unit` rc=0. 조건 누락 게이트가 그 안에서 돈다.
3. 진입점 하나(예: tokens `.`)에서 조건을 빼면 2 가 빨강이 되고, 되돌리면 초록(손 확인).

### 크기 게이트 (build 끝)

4. `pnpm build` 출력 끝에 크기 게이트가 돌고 rc=0.
5. 한 패키지의 basis·max 를 규칙대로 작게 고치면 `pnpm build` 가 크기 초과로 실패하고, 되돌리면 통과(손 확인).

### 배포물은 그대로

6. build 뒤 dist JS 에서 `@centurio1987/*` 는 외부 import 로 남고, 다른 패키지의 소스 경로(`/src/`)를 끌어온 줄이 0건.
7. `.d.ts` 가 다른 패키지 타입을 외부 import 로 둔다(core·visualization-style-guide-catalog 로 본다).
8. `npm pack --dry-run` 목록이 main 빌드와 견줘 dist 밖 파일이 같고 dist 파일 수가 같다.

### 생성기

9. dist 없이 생성 스크립트 6개가 돌고, 그 뒤 `git diff --exit-code` 로 커밋된 색인 4개가 그대로다.

### 게이트 5종 (전부 초록이어야 완료)

```bash
pnpm typecheck
pnpm build                      # ← 끝에서 번들 크기 게이트가 돈다
pnpm test                       # Storybook 은 지금처럼 dist 를 읽는다
pnpm --filter storybook build
pnpm test:unit                  # ← 번들 크기 게이트가 빠지고 조건 누락 게이트가 들어온다
```
