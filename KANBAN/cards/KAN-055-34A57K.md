# KAN-055-34A57K — 트리 셰이킹·글꼴·키보드 수정분 배포 (사용자 실행 지시 후)

## 전략
### 무엇을 하는가

main에 쌓인 changeset(재수립 시점 다섯 장: KAN-051·052·053·054·058)으로 패키지 버전을 올려 GitHub Packages에 배포한다. 외부 앱은 배포본만 설치할 수 있으므로 이 카드가 끝나야 외부 앱이 보고한 네 문제(번들 크기·외부 글꼴·Drawer 포커스·Tabs/Select 키보드)가 그쪽에서 실제로 풀린다.

| 패키지 | 배포본 | 다음 | 근거 |
|---|---|---|---|
| core | 1.1.2 | 1.2.0 | 051 patch · 052·053·054 minor |

- 다음 버전은 `pnpm changeset status --verbose`, 배포본은 `npm view`로 확인했다.
- tokens·foundations·hooks는 올리지 않는다. 마지막 배포(6ea5789) 뒤 바뀐 것이 주석과 배포물 밖 시험 파일뿐이다. core·viz가 의존하는 tokens 1.3.0은 이미 레지스트리에 있다.

### 승인 규칙

main push와 Version PR 병합은 밖으로 나가는 일이라 **사용자의 분명한 실행 지시가 있어야 한다.** 그 지시가 나오기 전까지 이 카드는 백로그에 둔다. 카드를 할 일이나 진행 중으로 옮기는 일, 전략 재수립은 승인으로 보지 않는다.

- **push와 배포를 함께 지시받아야** 병합까지 간다. push만 지시받았으면 Version PR의 버전·CHANGELOG를 S1 표와 대조해 보고하고 멈춘다.
- 대조가 어긋나면 지시가 있어도 병합하지 않고 멈춰 보고한다.
- 카드 완료 때 카드 브랜치를 main에 병합해 다시 push하는 것도 밖으로 나가는 일이라 그때 따로 지시를 받는다.

지시를 받기 전에 사용자에게 알릴 것:
- `.github/workflows/release.yml:6-8`은 main push만으로 돈다. push하면 main의 로컬 커밋 전부(개수는 S1에서 센다, 칸반 커밋 포함)가 **공개 저장소에** 함께 나가고, changeset이 남아 있으므로 Version PR이 만들어진다.
- Version PR 병합이 곧 배포다.

### 흐름

1. 착수는 워크트리 `KAN-055-34A57K`에서 한다. 이 카드가 바꾸는 파일(package.json·CHANGELOG·changeset 소진)은 CI가 `changeset-release/main` 브랜치에서 만들므로 카드 브랜치에는 칸반 기록만 쌓인다. push는 main 체크아웃에서 한다.
2. S1 push 직전 점검 → S2 push · Version PR 대조 · 병합 → CI 배포 → S3 배포본 확인과 전달.
3. main 체크아웃은 여러 세션이 함께 쓴다. S1에서 점검한 커밋 뒤에 main이 움직였으면, 새로 들어온 커밋이 칸반 파일만 건드렸는지 확인한다. `packages/`나 `.changeset/`이 바뀌었으면 S1을 다시 한다.
4. 병합 뒤 origin/main에 release 커밋이 생기므로 로컬 main에 병합한다(`git pull --no-rebase`). 카드 완료 push로 release가 한 번 더 돌아도 changeset이 다 소진돼 있어 이미 있는 버전은 건너뛴다(KAN-043 때 같은 흐름이 초록이었다).

## 실행 계획
- [ ] `S1` push 직전 점검 — main 체크아웃에 MERGE_HEAD·충돌 표시(UU)가 없는지 본다. `.changeset/*.md` 목록과 `pnpm changeset status --verbose`로 버전 표를 다시 내고, push할 main 커밋에서 게이트 5종을 돌린다. origin보다 앞선 커밋 수를 센다. 완료 기준: 패키지·배포본·다음 버전 표, 게이트 5종 초록, 점검한 커밋 해시와 나갈 커밋 수
- [ ] `S2` 배포 — 사용자가 push와 배포를 함께 분명히 지시한 뒤에만 한다. 지시 전에 「S1에서 센 커밋이 공개 저장소에 나가고 release.yml이 돈다」를 알린다. main이 S1 커밋 뒤에 움직였으면 새 커밋이 칸반 파일뿐인지 확인한다 → `git push origin main` → Version PR의 버전·CHANGELOG를 S1 표와 대조 → 같으면 병합, 다르면 멈춘다 → release 실행 초록 확인 → 로컬 main에 origin/main 병합. push만 지시받았으면 대조까지 하고 멈춘다. 완료 기준: 레지스트리에 새 버전, release 실행 둘(PR 생성·배포) 초록
- [ ] `S3` 배포본 확인과 전달 — 스크래치 폴더에 외부 앱과 같은 길(`npm install`)로 새 버전들과 react·react-dom을 받는다. 각 패키지는 `node_modules/@centurio1987/bbangto-ui-<n>/package.json`의 `exports['.'].import`가 가리키는 **파일 절대경로**를 진입점으로 삼아, `bundle-budget.json`의 `measure` 설정으로 대표 export 하나와 전체를 잰다. 값이 저장소 dist 실측(basis)과 크게 다르면 측정 실패로 보고 원인부터 찾는다. core를 Node에서 이름으로 import해 의존(tokens 1.3.0)이 풀리는지 본다. 외부 앱에 전할 문구(새 버전 · `fonts` prop · 키보드 지원 범위 · 동작이 바뀐 곳)를 수행 내역에 남긴다. 완료 기준: 배포된 패키지 모두 상한 이하(core `Button` 단독 7,168B 이하), import 성공, 문구 기록

## 검증
### 무엇이 나오면 끝인가

- GitHub Packages에 core 1.2.0 · visualization 0.4.0 · style-guide-catalog 0.3.2 · visualization-style-guide-catalog 0.3.1이 있다(S1에서 표가 바뀌면 그 표를 따른다)
- release 워크플로 실행이 초록이다(test:unit 단계 포함)
- 배포본을 설치된 dist 파일 경로 진입점 + `bundle-budget.json` 측정 설정으로 재면 배포된 패키지의 대표 export·전체가 `max` 이하다. core `Button` 단독은 7,168B 이하다(1.1.2에서는 324,410B, 저장소 dist 기준값 4,622B). 값이 기준값과 크게 다르면 통과로 치지 않는다
- 배포된 core의 `package.json` 의존이 `workspace:*`가 아니라 실제 버전이고, Node에서 import된다
- 외부 앱에 전할 문구가 수행 내역에 있다. 동작이 바뀐 곳(Tabs 화살표 자동 선택 · Card `onClick` 단독이면 interactive · 외부 `onKeyDown`의 `preventDefault` 규칙 · `makeShowcase` 넷째 인자)을 빠뜨리지 않는다
