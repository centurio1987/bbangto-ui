# bbangto-ui README (`bbangto-readme`)

레포 루트 `README.md` 한 장이다. 독자는 **이 레포를 처음 보는 개발자**이고, 이 글의 성패는
"잘 썼는가"가 아니라 **독자가 자기 사례를 찾아 그 절차를 끝까지 실행했는가**로 갈린다.

## 무엇을 위한 글인가

세 가지를 순서대로 해내게 한다.

1. 자기가 만들려는 것을 라우팅 표에서 찾는다.
2. 그 사례의 번호 절차를 따라 화면에 무언가를 띄운다.
3. 필요하면 자기만의 style guide 까지 저작한다.

3번이 이 README 가 이전 판과 갈리는 지점이다. 개정 전 README(174줄)는 패키지 표와
설치 스니펫뿐이라 **저작 경로가 한 줄도 없었다.** 사례 목록에서 저작 사례가 빠지면
이 글은 이전 판으로 되돌아간 것이다.

## 사실은 어디서 오는가

수치의 정본은 매니페스트 넷뿐이다(BR2).

| 무엇 | 정본 |
| --- | --- |
| UI style guide preset 수 | `packages/style-guide-catalog/catalog.manifest.json` |
| foundation(브랜드 프리셋) 수 | `packages/foundations/foundation.manifest.json` |
| viz style guide preset 수 | `packages/visualization-style-guide-catalog/catalog.manifest.json` |
| viz 유형 수 | `packages/visualization/type.manifest.json` |

세어서 쓴다. 이전 판이 적었던 수를 옮겨 오지 않는다 — 그 수들은 이미 실측과 어긋나 있었고,
**틀린 수치 하나가 나머지 문장의 신뢰까지 같이 깎는다.**

코드의 정본은 각 패키지의 공개 export 다(BR1). import 줄에 적을 심볼은 그 패키지에서
실제로 나오는 것만 쓴다. 확인 못 한 API 를 그럴듯하게 적으면 그건 문서가 아니라 함정이다.

## 절 여섯

| 절 | 답해야 할 질문 | 분량 감각 |
| --- | --- | --- |
| 한 줄 정의와 히어로 | 이게 무엇이고 무엇을 해 주는가 | 이미지 + 3~5줄 |
| 사례 라우팅 | 나는 어느 사례인가 | 표 하나 + 표를 읽는 법 1~2줄 |
| 사례 본문 | 그래서 무엇을 어떤 순서로 하는가 | 사례마다 네 자리 |
| 패키지 표 | 무엇이 들어 있는가 | 표 하나 |
| 개발과 품질 게이트 | 기여하려면 무엇을 통과시켜야 하는가 | 명령 블록 + 게이트 목록 |
| 함께 보기 | 더 깊이 보려면 어디로 | 링크 목록 |

### 한 줄 정의와 히어로 (`hero`)

레포 이름 · 히어로 이미지 · 한 줄 정의 · 이 README 가 무엇을 안내하는지까지다.
설치 명령을 여기 두지 않는다 — 설치는 사례마다 다르고, 여기 하나를 박아 두면
독자는 자기 사례가 아닌 패키지를 먼저 깐다.

### 사례 라우팅 (`routing`)

**이 글에서 가장 먼저 완성해야 하는 절이다.** 독자는 여기서 갈라지고, 갈라지지 못하면
나머지를 다 읽어도 자기 것을 못 찾는다.

- 행마다 **목적을 앞에, 패키지를 뒤에** 둔다(BR6). "core + tokens" 가 아니라
  "앱에 컴포넌트를 얹는다 → core + tokens" 다.
- 각 행은 해당 사례 절의 앵커로 링크한다. 링크가 실제로 걸리는지 확인한다(BR7).
- 사례 경계가 겹치면 표가 아니라 사례 정의가 잘못된 것이다. 표에서 조건을 덧붙여
  가리지 말고 사례를 다시 가른다.

하지 말 것: 레이어 이름(atom·molecule·pattern)으로 가르기. 그 축은
`DESIGN_SYSTEM_GUIDE.md` 의 것이고, 처음 온 독자는 그 이름으로 자기를 알아보지 못한다.

### 사례 본문 (`cases` → `cases.case`)

사례 하나가 반복 단위다. 네 자리를 **이 순서로** 채운다(BR3).

1. **누가 언제 쓰나** (`cases.case.audience`) — 독자가 "이게 나다"를 판정할 수 있게 쓴다.
   상황으로 쓰고 기능으로 쓰지 않는다. 2~4줄.
2. **설치** (`cases.case.install`) — 그 사례에 필요한 패키지만 담은 실행 가능한 명령 하나.
   전 패키지를 한 줄에 몰아 적지 않는다. 이 사례에 안 쓰는 패키지를 깔게 하면
   독자는 자기가 무엇을 쓰는지 모른 채 시작한다.
3. **최소 동작 코드** (`cases.case.minimal`) — **붙여 넣으면 화면에 무언가가 나오는**
   가장 작은 코드다. 잘라 낸 조각(`...` 로 생략된 본문)을 싣지 않는다.
   Provider 가 필요하면 Provider 까지 포함한 한 덩어리로 싣는다.
   import 심볼은 전부 실제 export 여야 한다(BR1).
4. **그다음 걸음** (`cases.case.next`) — 여기서 만족한 독자가 다음에 갈 곳.
   다른 사례로 보내거나, 카탈로그·가이드 문서로 보낸다. 마지막 사례도 비우지 않는다 —
   갈 곳이 정말 없으면 그 사례가 마지막인 이유를 한 줄로 적는다.

절차는 번호 목록이고 산문이 아니다(BR5). 한 항목 = 독자가 수행할 한 동작이고,
명령·코드 블록은 그 항목 **안에** 붙인다.

#### 「그다음 걸음」이 self-check-closing 을 겸한다

`ppangtolab-teacher` voice 는 문서를 「스스로 점검하기」 문제로 닫는 장치
(`self-check-closing` · `midway-check-question`)를 갖는다. **이 글에서 그 장치가 사는 자리는
문서 끝의 별도 절이 아니라 사례마다 붙는 네 번째 자리(`cases.case.next`)다.**

그렇게 정한 이유가 둘이다. 하나는 위치다 — 독자는 사례 하나를 막 끝낸 그 자리에서
"방금 한 것이 무엇이었고 다음은 무엇인가"를 받아야 점검이 값한다. 문서 맨 끝의 퀴즈는
열 개 사례 중 자기가 읽은 하나와 이미 멀어져 있다. 다른 하나는 매체다 — OSS README 는
드문드문 훑는 문서라 마지막 절까지 읽는 독자를 전제할 수 없다.

그래서 「그다음 걸음」은 링크 나열이 아니다. **방금 무엇을 할 수 있게 됐는지 한 줄로 확인시키고,
그다음 갈 곳을 건다.** 그 한 줄이 self-check 이다.

> 이제 `Button` 하나가 라이트 테마 토큰으로 그려집니다. 색을 바꾸고 싶으면 사례 4로,
> 섹션 통짜가 필요하면 사례 2로 가세요.

문서 끝에 「스스로 점검하기」 절을 따로 만들지 않는다.

#### 저작 사례(직접 룩을 만든다)는 특별히 챙길 것

UI·viz 두 저작 사례는 최소 동작 코드가 "preset 하나를 쓰는 법"이 아니라
**preset 하나를 만드는 법**이다. 그러니 네 번째 자리가 무겁다 — 대비(WCAG) 게이트와
매니페스트 등재까지 이어져야 저작이 끝난다. 그 두 단계를 "그다음 걸음"으로 미루지 말고
절차 번호 안에 넣는다. 등재되지 않은 preset 은 카탈로그에서 안 보이고,
독자는 자기가 뭘 빠뜨렸는지 모른다.

### 패키지 표 (`packages`)

무엇이 들어 있는지 한눈에 보이는 자리다. 라우팅 표를 되풀이하지 않는다 —
라우팅은 **목적**으로 가르고 이 표는 **내용물**을 적는다. 카탈로그 수를 적는 칸은
매니페스트 실측값이다(BR2).

### 개발과 품질 게이트 (`dev`)

기여 사례가 착지하는 자리다. 실행 명령을 그대로 복사할 수 있게 블록으로 싣고,
게이트가 무엇을 막는지 한 줄씩 붙인다. 명령만 나열하면 독자는 하나가 빨간불일 때
그게 자기 잘못인지 선행 상태인지 모른다.

### 함께 보기 (`links`)

BR4 가 넘기기로 한 것들의 착지점이다. 링크마다 **거기 가면 무엇이 있는지** 한 줄을 붙인다.
제목만 나열한 링크 목록은 독자가 안 누른다. 존재하는 파일만 링크한다(BR7).

## 한 장 자립의 경계

BR4 는 "짧게 쓰라"가 아니라 **"먼저 읽어야 할 문서를 만들지 마라"** 다. 판정은 하나로 한다.

> 독자가 이 README 만 열어 두고 사례 절차를 끝까지 실행할 수 있는가.

- 실행에 필요한 것 → README 에 싣는다(설치·코드·명령·게이트).
- 실행하지 않아도 되는 것 → 링크로 넘긴다(설계 근거, atom/molecule/block/pattern 기준,
  토큰 체계의 이론, 채택 메타의 네 축).

애매하면 실행 쪽으로 판단한다. 넘긴 것을 되찾아 오는 비용보다 못 넘긴 것을 읽는 비용이 싸다.
